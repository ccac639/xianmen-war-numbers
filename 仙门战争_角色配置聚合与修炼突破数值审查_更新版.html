三、综合资质 V2：加入境界后的正式计算口径

InnateAptitude = clamp( 0.30 × SpiritRootScore + 0.25 × TalentScore + 0.20 × InsightScore + 0.15 × BloodlineScore + 0.10 × FateScore, 0, 100 ) RealmFactor = 1 + 0.20 × StageIndex / 25 FinalAptitude = clamp(round(InnateAptitude × RealmFactor), 0, 100) StageIndex: 凡人=0，项目最后一个境界=25。

这次保留原先 30/25/20/15/10 的五维权重，并把境界作为独立修正因子，而不是把境界偷偷塞进某个单项。这样同一套天赋/灵根/血脉配置在不同境界会得到不同资质，但不会改变人物的基础 N。

为什么用倍率而不是硬加分：低资质角色会随境界成长，高资质角色仍保持高位，同时最高结果统一封顶 100；从凡人到项目第26阶段，境界最多提供 +20% 的资质成长。

六、互通引用与具体问题

  • @CharacterTmpl → @UnitAttrTmpl：属性 ID 1～16 可在本文件中找到，属于可解析引用。
  • @RoleSpiritRoot：灵根范围大量引用 81～88 等属性 ID，而本文件 @UnitAttrTmpl 只到 79；这意味着根属性继续解析需要外部属性表。
  • @BloodTmpl：addValueId 使用 50001～50114 等 ID，而本文件 @UnitAttrTmpl 并无对应 ID；同样属于外部/后续映射。
  • @RoleTalent：属性 ID、技能修炼 ID、生成灵根 ID 等多类字段并非全部能在 8 张表内部闭环；不能把“字段存在”误判为“字段语义已完成”。
  • @OneAttributeTransition：当前 5 条转换记录的类型数量与数值数量逐条对齐，结构没有发现长度错位。
  • @CharacterTmpl 策略：4 组概率串均应按 10000 分母解释；当前行级校验未发现总和异常。
建议的程序架构：所有跨表 ID 在进入 EffectPool 之前都必须经过 resolveReference()；解析不到时记录 warning + sourceId，而不是静默当成 0。
