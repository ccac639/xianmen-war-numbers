四、突破系统

4.1 可确认的 MOD 字段

参考 @RoleState 确实存在 breakthroughProbability、exp、failure_vigour_down、needTaoistHeart、needBreachProbability 等突破相关字段。它可以作为《仙门战争》的突破数据结构参考。

4.2 不能直接冻结的原因

MOD 使用的修为与突破表按其自身的“九层/大圆满”结构组织，而《仙门战争》采用“炼气1～9 + 其他境界初中后圆满”的26阶段结构。 因此 MOD 的 exp 与突破概率必须重新映射，不能直接当作《仙门战争》的正式表。

4.3 推荐突破公式 [AI候选]

FinalBreakthroughRate = clamp( BaseBreakthroughRate + BreakthroughFlatPool + BreakthroughPercentPool, 500, 9500 )

建议统一使用 0～10000 的整数万分比存储概率。项目资料本身也要求概率使用整数而非浮点。

六、统一配置校验规则

6.1 天赋

  • 没有 exclusiveId：允许共存。
  • exclusiveId>0：同一互斥组最多一个。
  • 同组之外仍要检查 effect_scope 冲突和重复来源。

参考 MOD 的 @RoleTalent 实际存在 exclusiveId，因此这条规则可以直接落地。

6.2 灵根

  • 角色只拥有一个“灵根记录”。
  • 灵根记录内部可以有多个元素组成，例如双灵根、三灵根、五灵根。
  • 灵根只负责修炼效率、法力/法术亲和等指定方向，不改变境界 N。

6.3 血脉

  • 最多3条。
  • 每条血脉最多3个血脉天赋：这是当前项目规则，不是 MOD 原生字段。
  • 血脉互斥必须单独建立 bloodline_conflict_group。
  • 血脉模板通过 addValueId → 属性模板 → EffectPool，只结算一次。

6.4 命格

  • 星格最多1个。
  • 道格最多1个。
  • 两类默认可以共存。
  • 只有明确 cross_conflict 才互斥。

6.5 体质

  • 最多6种。
  • 与天赋一样使用 exclusiveId 思路，但 exclusive namespace 必须独立。
  • 数量上限与互斥组应该同时存在：前者限制总量，后者限制冲突组。

七、统一角色效果聚合层

RawRoleConfig ↓ validateRoleConfig() ↓ EffectiveRoleConfig ↓ resolveTalentEffects() resolveSpiritRootEffects() resolveBloodlineEffects() resolveFateEffects() resolveConstitutionEffects() ↓ deduplicateEffects() ↓ aggregateByScope() ↓ EffectPool ↓ BaseRealmPanel ↓ FinalRolePanel / Cultivation / Breakthrough

统一 Effect 结构

{ sourceType: "talent | spirit_root | bloodline | fate | constitution", sourceId: number, scope: "combat_hp_pct | combat_mp_pct | combat_attack_pct | combat_defense_pct | combat_speed | cultivation_speed_pct | breakthrough_success_pct | attribute_growth_pct | skill_effect_pct", target: string, mode: "flat | percent_add | conditional", value: integer, stackable: boolean, cap: integer, priority: integer, conditionId: optional }

战斗属性

FinalCombatStat = floor( BaseRealmStat * (10000 + CombatPctPool) / 10000 ) + CombatFlatPool

修炼速度

FinalCultivationSpeed = floor( BaseCultivationSpeed * (10000 + CultivationPctPool) / 10000 ) + CultivationFlatPool

属性成长

ActualGrowth = floor( BaseGrowth * (10000 + AttributeGrowthPctPool) / 10000 ) + GrowthFlatPool

去重规则

同一个 effect_id / source / target / scope 不能从两条路径重复写入。 例如 BloodTmpl → addValueId → UnitAttrTmpl 后，不能再从 BloodTmpl 直接把同一效果加一次。

八、三套伤害公式候选

公式 A：攻击减防

D = max(1, Attack - Defense)

优点：直观。缺点：防御稍高就迅速进入最低伤害区；不建议作为最终公式。

公式 B：百分比减伤

DR = clamp( Defense / (Defense + 2 × Attack), 0, 80% ) D = Attack × (1 - DR)

优点：不会轻易出现“完全打不动”。缺点：防御的收益较平滑，参数调节需要软上限。

公式 C：混合型

EffectiveDefense = floor(Defense × (10000 - EffectivePenetration) / 10000) D = floor( Attack² / (Attack + 2 × EffectiveDefense) )

当前 data.html 实际已经使用这一结构，是与 ATK=N、DEF≈0.4N、HP=10N 最匹配的候选公式。

核心伪代码

function buildEffectiveRole(rawRole) { const valid = validateRoleConfig(rawRole); if (!valid.ok) return { ok:false, errors:valid.errors }; const effects = [ ...resolveTalentEffects(valid.talents), ...resolveSpiritRootEffects(valid.spiritRoot), ...valid.bloodlines.flatMap(resolveBloodlineEffects), ...resolveFateEffects(valid.starFate), ...resolveFateEffects(valid.daoFate), ...valid.constitutions.flatMap(resolveConstitutionEffects) ]; const uniqueEffects = deduplicateEffects(effects); const pools = aggregateEffects(uniqueEffects); const base = buildRealmBasePanel(rawRole.realmStageId); return { ok: true, base, pools, panel: applyCombatPools(base, pools), cultivation: applyCultivationPools( getBaseCultivation(rawRole.realmStageId), pools ), breakthrough: applyBreakthroughPools( getBaseBreakthrough(rawRole.realmStageId), pools ) }; }
这一层的目标不是“把所有系统都算一遍”，而是建立唯一的效果入口。任何天赋、灵根、血脉、命格、体质效果都先转换成统一 Effect，再进入对应作用域池，最终只结算一次。
